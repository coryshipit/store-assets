# Store Assets 测试策略

## 1. 文档目的

本文档记录 Store Assets 在当前 Phase 1 的测试策略设计，用于替代“完整 dry-run 必须作为主要发布门禁”的假设。它定义测试目标、证据层级、触发条件、结果判定和后续演进方向。

Store Assets 是由工作流规范、模板、目录约定和 agent 指令组成的工作包，不是传统可执行程序。测试应优先验证该工作包可控制的文件结构、规则和状态变换；不能将某个 agent 或 headless 执行器完成长对话任务的能力，当作项目正确性的唯一依据。

本文档是 Task G 的设计输入。方案被接受后，应同步更新 `docs/QA.md`，再将其中稳定、无歧义的检查逐步实现为可重复命令或小型验证脚本。

## 2. 已知证据与问题

截至 2026-08-10：

- 旧的单会话完整 dry-run 曾运行三次，均在不同阶段停止或沉默，未取得完整行为 `PASS`。
- 已知原因包括长上下文、headless 环境无法处理交互确认，以及执行器沉默时缺少可判定的失败信息。
- 将流程拆为四个 fresh-agent 阶段可以缩小单次任务范围，但不能保证端到端流程可靠，也不能消除 agent 或执行器的非确定性。
- `v0.1.1` 发布时，维护者基于项目曝光有限和 Task G 尚在研究，明确接受了跳过 staged dry-run 的例外。该版本已完成静态检查以及实际 release asset 的人工下载、解压和目录确认，但没有行为 `PASS`。

因此，现有 staged dry-run 保留其诊断价值，但不适合作为当前主要发布门禁。

## 3. 测试目标与非目标

### 测试目标

- 确保 copyable starter kit 的目录、入口文件、模板和发布包符合已记录的约定。
- 确保工作流、rulebook 和模板对生命周期、状态机和文件职责使用一致术语。
- 确保 agent 在固定事实输入下，能够独立执行受影响的关键场景，并产出符合不变量的文件。
- 确保每个公开 release 的实际下载包可用且与对应 tag 一致。
- 让失败、环境异常和未验证状态可区分、可追溯，避免将不确定结果误记为通过。

### 非目标

- 不测试真实商店的上传、审核或发布行为；Store Assets 不是商店 API、CLI 或自动上传服务。
- 不自动判断营销文案或产品事实在语义上完全真实；这仍依赖可验证事实源和人工审阅。
- 不要求每次纯文案改动执行完整 agent 生命周期。
- 不在规则和 fixture 尚未稳定时，过早实现通用 CLI 或复杂 CI 服务。

## 4. 测试分层

当前推荐采用以下四层，而不是单一 dry-run：

| 层级 | 验证对象 | 主要证据 | 发布角色 |
| --- | --- | --- | --- |
| A. 确定性 conformance 检查 | 目录、模板、占位符、术语、链接、敏感内容和 release archive | 可重复命令、检查表、脚本输出 | 必须通过 |
| B. Agent 场景测试 | fresh agent 对单个生命周期步骤的可恢复性和文件产物 | 固定 fixture、预期不变量、产物差异 | 高风险变更的补充证据 |
| C. 人工 release 检查 | GitHub 实际 asset、用户入口和安装路径 | 下载、解压、文件检查 | 每次发布必须完成 |
| D. 未来自动验证 | 已稳定且无歧义的规则 | 小脚本、GitHub Actions 或未来 CLI | 逐步替代人工重复检查 |

### 4.1 A 层：确定性 conformance 检查

这层是当前最适合作为发布门禁的检查，因为输入、输出和判定均可明确描述。至少应覆盖：

- `starter-kit/` 的目录布局与已接受的设计一致，包括 Microsoft Store 目录和 Apple/Google 的保留 skeleton。
- 静态 `README.md` 存在且不包含 `{{...}}` 占位符；工作流、rulebook 模板及必需目录存在。
- 模板包含 `template_version`；模板内容变更时版本同步增加。
- 仅模板和已声明的 rulebook 示例/文件骨架可以出现指定占位符；生成物不能残留项目级占位符。
- 工作流、rulebook、README 和 release 文档中的路径、相对链接及生命周期术语一致。
- `current/`、`release-prep/`、`submissions/`、状态机和发布提升规则没有互相矛盾的定义。
- starter kit 中没有凭据、私密资料、未脱敏截图或意外二进制内容。
- release zip 只有 `store-assets/` 顶层目录，仅包含 starter kit 内容，且存在静态 README、workflow 和 rulebook 模板。

现有 release workflow 已验证 archive 的一部分约束。后续应将上述稳定规则整理为可重复的检查表，或以小型仓库脚本实现；不需要等待通用 CLI 才开始执行。

### 4.2 B 层：Agent 场景测试

保留原本的四个阶段，但将其改为彼此独立、可判定的场景测试，而非要求一个长会话完成整个流程。

| 场景 | 固定输入 | 必须验证的不变量 |
| --- | --- | --- |
| 初始化 | 产品名、`microsoft-store`、默认 locale、已发布版本和事实表 | 生成命名正确、项目变量已解析的 rulebook；不创建不相关 store 内容 |
| 准备并记录 | 现有 `current/`、一个更新事实表和 submission 变量 | `current/` 未修改；建立完整 `release-prep/` 候选快照；只创建一个 `Draft` record |
| 跟踪提交 | 已存在的 Draft record 和明确的 store 事件 | 仅更新既有 record 状态；不创建第二个活跃 submission；不修改候选资产 |
| 发布提升 | 已存在的准备内容、submission record 和明确 go-live 确认 | 以候选树替换受影响的 `current/<locale>/`；记录 `Published` 与日期；清理完成的 prep |

场景产物不应要求文案逐字一致。判断重点是目录、字段、状态、占位符、禁止修改的文件和已声明事实边界。

fresh agent 仍然有价值：它能验证下一位 agent 是否只凭工作包内文件恢复任务上下文。但这只证明文档可恢复性，不等同于单个 agent session 的端到端稳定性。

### 4.3 C 层：人工 release 检查

每个 release 在 draft 或发布后都应由维护者完成：

1. 下载对应 tag 的 release asset。
2. 解压并确认只有一个顶层 `store-assets/` 目录。
3. 打开静态 README、workflow 和 rulebook 模板，确认入口文件可读。
4. 确认 asset 名称、tag 和 release notes 对应同一版本。
5. 在 roadmap 的 release log 中记录结果。

这层成本较低，且直接验证用户实际获得的产物，因此是必需门禁。

### 4.4 D 层：未来自动验证

当规则、fixture 和预期不变量稳定后，优先自动化 A 层中的确定性检查。建议演进顺序：

```text
明确检查表
  -> 可重复命令或小脚本
  -> release workflow 中的稳定检查
  -> 必要时才考虑 store-assets validate 或 CI 集成
```

不要先实现会固化不稳定规则的通用验证 CLI，也不要将需要产品语义判断的内容伪装为完全自动化检查。

## 5. Fixture 与预期产物

Agent 场景测试需要可复现输入，不能依赖维护者临时记忆或仓库外会漂移的事实表。

- 将最小 fixture 的事实定义、任务 prompt 和预期不变量版本化保存到仓库。
- 实际运行目录仍在仓库外的临时位置，避免 agent 修改仓库或污染 fixture 源。
- fixture 只包含虚构且可验证的产品事实，不包含真实账号、用户数据、截图、密钥或私有文档。
- 每个场景从其定义的输入状态开始；阶段间不允许人工修补文件后再判定成功。
- 预期结果优先表达为结构与字段断言，而不是要求生成文案完全相同。

具体 fixture 文件布局和是否引入验证脚本，属于本分支后续设计和试验的范围。

## 6. 结果判定与重试规则

所有测试结果使用以下枚举：

| 结果 | 定义 | 处理 |
| --- | --- | --- |
| `PASS` | 所有适用断言满足，产物与预期不变量一致 | 记录证据并继续 |
| `FAIL` | 规则、文件产物或确定性检查明确不符合预期 | 修复后重新验证 |
| `INCONCLUSIVE` | agent 沉默、超时、工具崩溃或执行器无法判定，且没有足够证据归类为 PASS/FAIL | 记录环境与产物；同一场景最多重试一次 |

agent 沉默不能自动视为 PASS，也不能无限重试后放行。一次重试后仍为 `INCONCLUSIVE` 时：

- 记录场景、完整 prompt、执行环境、停止位置、已生成文件和与预期的差异。
- 区分“工作流指令不清楚”与“测试执行器不稳定”的假设，不能预先归因。
- 是否发布由 A 层和 C 层证据决定，并由维护者明确接受剩余风险；不得将 `INCONCLUSIVE` 写成行为测试通过。

## 7. 按变更选择测试

| 变更类型 | 必须执行 | 建议补充 |
| --- | --- | --- |
| 纯文案、导航或 release notes | 受影响文件的静态检查、链接检查 | 不需要 agent 场景 |
| workflow、rulebook、状态机、目录约定 | 全量 A 层检查 | 覆盖受影响的 B 层场景 |
| release workflow、打包或 Distribution 规则 | A 层 archive 检查 | C 层实际下载和解压 |
| 新 store adapter | 全量 A 层检查 | 该 adapter 的全部 B 层场景和 C 层检查 |
| 规则不清晰或 agent 行为出现回归 | 全量 A 层检查 | 设计针对性场景，不必运行无关场景 |

## 8. 发布门禁

在 Task G 的方案完成前，发布应至少具备：

- 适用的确定性 conformance 检查通过。
- release workflow 成功构建并上传 archive。
- 维护者完成实际 asset 的下载、解压和入口文件检查。
- release notes 来源文件已入库，并与 GitHub Release 正文一致。
- 若跳过适用的 Agent 场景测试或出现 `INCONCLUSIVE`，维护者在 roadmap 或 release 记录中明确接受该例外及原因。

Agent 场景测试在当前阶段不作为无条件阻塞门禁；当 Task G 证明其稳定、可重复且成本合理后，才重新评估其门禁地位。

## 9. 不建议的方案

- 不恢复单会话完整 dry-run 作为门禁：历史证据表明其在当前 headless 环境不稳定。
- 不把 staged dry-run 作为唯一验证：它无法覆盖确定性 package 错误，也无法证明真实 release asset 正确。
- 不要求每次变更都人工执行真实商店发布：这超出 Store Assets 的准备层边界，且成本和外部风险过高。
- 不立即实现复杂 CLI、SaaS 或 CI 服务：应先从稳定规则提炼最小自动化。

## 10. Task G 完成标准

Task G 在满足以下条件后才可标记完成：

- 已接受 A-D 四层职责、触发条件和发布门禁。
- 已定义 fixture 源、场景输入和每个场景的预期不变量。
- 已定义 `PASS`、`FAIL`、`INCONCLUSIVE` 及有限重试规则。
- 已明确哪些确定性检查以人工检查表执行，哪些已具备脚本化条件。
- `docs/QA.md`、`docs/ROADMAP.md` 与实际 release workflow 已同步该决策。
- 至少完成一次针对新策略的试验，并记录结论和仍存在的风险。

## 11. 本分支的工作边界

`testing/qa-strategy` 分支可同时包含：

- 测试策略、QA 文档、fixture 和确定性检查的设计或实现。
- 测试过程中发现的 Starter Kit 规则缺陷修复。

为保持结论可审阅，测试策略/工具、fixture、Starter Kit 规则修复和结果记录应拆分为独立 commit。单次运行日志不提交到仓库；仓库只保留可复用的规范、fixture、检查机制和经过确认的结论。
